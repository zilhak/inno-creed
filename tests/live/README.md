# 라이브 스모크 테스트

`cargo test`(순수 함수 단위 테스트)와 도구 표면 스냅샷은 **"구조가 같다"**만 보장한다.
실제 아마란스 API 왕복이 되는지는 증명하지 않는다. 이 스크립트가 그걸 증명한다 — 릴리즈된
바이너리를 MCP 클라이언트로 직접 구동해 도구 55개를 실호출한다.

## ⚠️ 이건 진짜 데이터를 건드린다

회의실이 실제로 예약되고, 개인 일정이 생기고, 결재라인이 만들어지고, 본인 앞으로 메일이
발송된다. 전부 즉시 되돌리지만 **"잠깐 존재했다"는 사실 자체는 남는다.**

**CI에 넣지 말 것.** 넣어도 스크립트가 거부하지만, 애초에 그런 용도가 아니다.

## 실행

```sh
cargo build --release
cp tests/live/fixtures.example.json tests/live/fixtures.json   # 최초 1회, 본인 값으로 편집
INNO_CREED_LIVE=$(date +%Y%m%d) python3 tests/live/live_test.py
```

터미널이 대화형이면 확인 문구(`실행합니다`)를 한 번 더 입력해야 진행한다.

종료 코드: `0` 전부 통과 · `1` 실패 또는 잔여물 있음 · `2` 승인 게이트에 걸려 실행 안 함.

### 상신 시나리오 (별도 opt-in)

```sh
INNO_CREED_LIVE=$(date +%Y%m%d) INNO_CREED_LIVE_SUBMIT=1 python3 tests/live/live_test.py
```

⚠️ **결재선의 사람들에게 실제로 결재요청 알림이 간다.** 문서는 몇 초 뒤 완전 삭제되지만
**알림은 회수되지 않는다.** 그들에게 미리 양해를 구한 뒤에만 켤 것. 이것 하나 때문에 기본 실행에서
빠져 있다 — 잔여물 문제가 아니다(아래).

`probe` 바이너리가 필요하다: `cargo build --release --bin probe`.

## 안전장치 4겹

### ① 승인 게이트

| 검사 | 동작 |
|---|---|
| `CI`/`GITHUB_ACTIONS`/`GITLAB_CI`/`JENKINS_URL` 등 17종 중 하나라도 설정됨 | 즉시 중단 |
| `INNO_CREED_LIVE` 가 **오늘 날짜(YYYYMMDD)** 가 아님 | 중단 |
| stdin 이 TTY | 확인 문구 입력 요구 |

`INNO_CREED_LIVE` 값이 오늘 날짜인 이유: **CI 설정 파일에 상주시킬 수 없게** 하기 위해서다.
하루만 지나면 무효가 되므로 "한 번 넣어두고 잊는" 경로가 성립하지 않는다. 반대로 사람이나
에이전트가 의도적으로 돌릴 때는 `$(date +%Y%m%d)` 한 조각이면 된다.

### ② 금지 도구 물리 차단

`attendance_clock_in` · `attendance_clock_out` · `delete_temp_approval` 은 `Mcp.call()` 진입부에서 **예외를 던진다.**
주석으로 "쓰지 마세요"를 적어두는 것과 다르다 — 나중에 누가 실호출 코드를 추가해도 실행되지 않는다.
`submit_approval`·`cancel_approval` 도 `INNO_CREED_LIVE_SUBMIT=1` 이 없으면 똑같이 차단된다.

`send_mail` 은 `to` 인자 지정 자체를 차단한다(미지정 = 본인 발송). 남에게 갈 경로가 없다.

역방향 검사도 있다: 서버의 `tools/list` 와 대조해 **호출도 안 되고 금지 목록에도 없는 도구**가
있으면 `도구_커버리지` FAIL. 도구를 새로 추가하고 점검을 안 짜는 것을 잡는다.

### ③ 쓰기 좌표 고정 + 마커 불변식

- 쓰기 대상(회의실 `resSeq`, 며칠 전인지)은 **`fixtures.json` 에서만** 온다. 코드에 좌표가 없다.
- 날짜는 실행 시점에 계산한다 — 14~90일 전의 평일. 하드코딩된 날짜가 낡아 오늘로 다가오는 사고가 없다.
- **사전 확인**: 고른 날의 대상 시간대(10:00–11:00, 12:30–13:30)에 그 회의실 예약이 이미 있으면
  하루씩 더 과거로 물러나 빈 날을 찾는다. 남의 실제 예약과 겹치는 상황을 만들지 않는다.
- 생성물 제목엔 전부 `marker`(`[live-test]`)를 붙인다.
- **삭제·취소는 "우리가 방금 만든 id" AND "그 객체 제목에 marker 가 있음"이 둘 다 참일 때만** 실행한다.
  둘 중 하나라도 어긋나면 손대지 않고 잔여물로 신고한다. 남의 예약·일정·메일을 지울 코드 경로가 없다.

### ④ 잔여물 대장 (`leaks.json`)

생성하는 즉시 `tests/live/leaks.json` 에 기록한다 — `kill -9` 로 죽어도 흔적이 남는다.
`finally` 에서 역순으로 정리하며 대장에서 지우고, 전부 정리되면 파일 자체를 삭제한다.
정리 못 한 게 남으면 **수동 정리 방법과 함께** 남기고 `exit 1`.
다음 실행은 본 점검을 시작하기 전에 그 대장부터 청소한다.

## 파일

| 경로 | git | 내용 |
|---|---|---|
| `live_test.py` | ✅ 추적 | 드라이버 |
| `fixtures.example.json` | ✅ 추적 | 자리표시자 |
| `fixtures.json` | ❌ 무시 | 실제 개인값(사번·회의실 seq·이름) — **이 저장소는 public이다** |
| `leaks.json` | ❌ 무시 | 잔여물 대장(정상 종료 시 자동 삭제) |

## 상신은 왜 되돌아가는가 (실측 2026-08-06)

"근태 양식은 HP 근태 레코드가 남아 못 지운다"는 **틀린 걱정이었다.** docId 141760으로 실측:

```
상신 전 HP 레코드                 59건
submit_approval                   docId 141760 → appSq 33147 생성
cancel_approval(purge=true)       결재취소 → 상신취소 → 임시보관삭제
상신 후                           59건 · appSq 33147 사라짐
read_approval                     2156 "삭제된 문서는 열 수 없습니다"
```

3단계 취소가 **HP 근태 레코드까지 회수한다.** 계정에 쌓여 있는 approState=2 잔여 57건은
2099 해결 **이전의 실패분**이다 — `create`는 성공했는데 `eap110A06`이 실패해서 취소할 eap 문서
자체가 없던 케이스라 고아로 남은 것이고, 하드삭제 API가 없어 지울 수 없다.

**따라서 진짜 위험은 "근태 양식이라서"가 아니라 "상신이 실패했을 때"다.** 그래서 이 시나리오는
상신 전후로 `at00001`(HP 신청 목록)을 찍어 신규 고아를 감지하고, 생기면 `HP근태레코드_고아` FAIL과
함께 appSq를 보고한다 — **자동 정리는 불가능하니 사람이 개인근태신청현황에서 확인해야 한다.**

### 결재선 사전 확인이 핵심 가드

상신 전에 `eap110A03`(읽기 콜, `docID=0`)로 **병합된 결재선**을 먼저 본다. 개인 라인이 그대로
쓰이는 게 아니라 양식필수 합의자·수신참조·시행자가 서버에서 합쳐지기 때문이다. 실측 예:

| 양식 | 결재 | 수신참조 | 시행 |
|---|---|---|---|
| 외근신청서(41) | 개인 라인 그대로 | **부서 3곳** | — |
| 연차휴가신청서(36) | 개인 라인 그대로 | 개인 1명 + 부서 2곳 | 개인 1명 |
| 휴직신청서(67) | 개인 라인 그대로 | 없음 | 없음 |

fixtures 의 `expectedApprovers`/`expectedRefer`/`expectedOper` 와 다르면 **상신하지 않고 FAIL** 한다.
회사가 양식 규칙을 바꿔 결재자·참조가 늘면 여기서 자동으로 멈춘다.

## 부작용을 인지할 것

- `read_notice` 는 게시글 **조회수를 1 올린다**. 되돌릴 수 없어 그대로 둔다(무해).
  최신 공지에 본문 이미지가 없는 날은 `bodyImage.artSeqNo` fixture의 글을 한 번 더 읽으므로
  그 글의 조회수도 1 오른다(fixture를 비우면 `download_body_image` 실다운로드가 SKIP 된다).
- `send_mail` → `delete_mail` 은 휴지통으로 보낼 뿐이다. 완전 삭제는 하지 않는다.
  발송 직후엔 서버가 아직 배달하지 않아 받은메일함에서 안 보일 수 있다 — **5초 간격으로 최대 30초까지
  기다렸다 지우고, 끝내 안 나타나면 성공으로 치지 않고 잔여물로 신고한다**(늦게 도착해 남는 것을 막는다).
  삭제 후에는 재조회로 실제로 사라졌는지 확인한다.
- `update_reservation` 은 서버가 **seqNum 을 재발급**한다. 대장 좌표도 함께 갱신하므로
  정리는 정상 동작하지만, 아마란스 화면에서 직접 찾을 땐 새 번호로 봐야 한다.
- 상신 시나리오(opt-in)는 **결재선 사람들에게 알림을 남긴다.** 문서는 지워져도 알림은 안 지워진다.
